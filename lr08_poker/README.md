# Оцінювання беклогу: як рахували

Студент: Злотенко Андрій Вікторович (`evilsdx`). Тема: Telegram-бот деканату. Варіант: V02.

## 1. Формат і масштаб

| Поле | Значення |
| --- | --- |
| Дата оцінювання | 2026-10-30 |
| Формат | Самостійна триточкова оцінка: optimistic, likely, pessimistic |
| Інструмент | Таблиця; PERT розраховано за формулою курсу |
| Історія-якір, оцінка 3 | S-03 — Замовлення довідки з переліку |
| Оцінено історій | 9 історій REL-1 |

S-03 обрано як якір, бо її сценарій і критерії приймання зрозумілі, а обсяг середній.

Story points показують відносний обсяг роботи з урахуванням складності та невизначеності. Це не години.

## 2. Історії з найбільшим розкидом

Подібний розкид є також у S-10: перед роботою треба погодити формат експорту та правила доступу до персональних даних. Для звуження оцінок потрібно уточнити ці питання з ІТ-службою та деканатом.

## 3. Конверт 1: переоцінка після нової інформації

| Поле | Значення |
| --- | --- |
| Історія | S-02 — Профіль студента |
| Чому саме вона | Після історії-якоря S-03 наступною за рангом історією з найменшим розкидом є S-02. |
| Оцінка до конверта | 3 points (O=2, M=3, P=5) |
| Оцінка після конверта | 5 points (O=3, M=5, P=8) |

Додаткову роботу створює перенесення наявних профілів із дублікатами, пропущеними полями та різними назвами груп. Та сама невизначеність може вплинути на S-01, S-09, S-04 і S-10. У першому раунді критерії описували функції бота, але не перенесення вже наявних записів. До початку роботи потрібно уточнити, які дані переносяться та як обробляються дублікати й записи без групи.

## 4. Сума першого релізу проти ємності варіанта

| Що | Значення |
| --- | ---: |
| Сума `final_estimate` історій REL-1 | 40 points |
| Ємність спринта V02 | 12 points |
| Спринтів до строку релізу | 10 тижнів / 2 = 5 спринтів |
| Місткість: ємність × спринти | 60 points |
| Різниця: місткість мінус оцінений обсяг | +20 points |

За початковою оцінкою обсяг першого релізу вкладається в розрахункову місткість із запасом 20 points. Це попередня оцінка, а не прогноз дати: фактична velocity стане відома після спринтів і буде використана для прогнозу в ЛР9.

## 5. Конверт 2: відповідь замовнику про години

Множення 40 points на 4 дає 160 годин арифметично, але це не оцінка трудомісткості й не число для договору. Story points показують відносний розмір історій і не мають сталого курсу в години. Години та суму в гривнях потрібно розраховувати за планом робіт і ставками, а не конвертувати з points. Після двох спринтів прогноз строку можна буде уточнити за фактичною velocity. Для домовленості із замовником доцільно погодити діапазон дат і перевірити його після перших спринтів.

## 6. Історії з карткою «не розумію»

Картку `?` у першому раунді не використано: для кожної з дев'яти історій є критерії приймання, достатні для початкової триточкової оцінки. Невідомі зовнішні залежності описані у `spread_note`.

## 7. Що показало оцінювання беклогу

Для S-02 потрібно уточнити перенесення наявних профілів: критерії описували збереження нового профілю та зміну групи, але не роботу з попередніми записами. У S-04 варто чіткіше розділити оформлення нового замовлення та перегляд попередніх, щоб не оцінювати ту саму функцію двічі. Найбільша технічна невизначеність стосується S-09, оскільки оцінка залежить від формату й поведінки API.
