Рішення про прийняття результату від імені замовника залишається за ST-01; погодження SC-04 і SC-05 фіксуються окремо. |

У A-03 Dev має `AR`: ця роль виконує й відповідає за результат свого пакета. Це нормально для симульованої команди з одним виконавцем на цю роль. У A-04 QA виконує перевірки як R, а відповідальність за приймання лишається на ST-01.

Активність, у якій A не в PM, — A-04. Якщо ST-01 не ухвалює рішення у погоджений строк, PM фіксує затримку, повторно надсилає результати перевірки й ескалує питання дзвінком замовнику; мовчання не вважається прийманням.

## 5. План комунікацій

| Поле | Значення |
| --- | --- |
| Рядків у `communication.csv` | 8 |
| Стейкхолдерів зі стратегією `manage_closely` і `keep_satisfied` | 5 |
| Регулярних рядків / рядків `on_event` | 6 / 2 |

Для V02 орієнтир REL-1 становить 10 тижнів, а спринт — два тижні. Тому формальний прогрес замовнику, юристу та службі безпеки передається раз на спринт; щотижневий короткий звіт Dev дає PM змогу помітити відхилення всередині ітерації. Для студентських сторін оновлення й запрошення надсилаються раз на спринт. Місячний звіт був би надто рідким для десятижневого плану. Повідомлення про критичні тригери йдуть дзвінком одразу після події.

Рядки поганої новини — C-03 і C-06. C-03 вмикається, якщо до віхи T-05 немає тестового доступу чи специфікації API або тест SSO не повертає потрібні атрибути за R-01 і R-02; повідомлення йде ST-05 телефоном. C-06 вмикається, якщо прогноз P85 перевищує цільову дату REL-1 або план WBS виходить за ліміт 900 годин за R-06; PM телефонує ST-01.

Окремі персональні дані студентів і технічні деталі доступу не розсилаються всім учасникам. Вони передаються лише сторонам, яким потрібні для їхніх рішень: ST-02, ST-05 та ST-06. Іншим надсилається стан роботи без даних конкретних студентів.
